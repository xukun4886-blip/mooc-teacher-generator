# Lecture 9 性能诊断与云端 SadTalker 最小改造方案

日期：2026-10-09（北京时间）。结论：优先验证“本机工作台＋单 GPU 云端 SadTalker”，先保留模型与输出配置，再评估常驻、照片预处理缓存和帧批量。主要瓶颈是人物渲染；现有证据不支持通过模型常驻把两小时任务直接压到十几分钟。

本轮仅诊断与设计，未运行任何生成、整课重跑、教师素材外传或付费接口，未修改代码、配置、数据库、素材、讲稿、审核和旧成果。新增本报告、[可复核的诊断数据](performance-cloud-sadtalker-diagnostic.json)，并在项目状态增加文档记录。下面的接口、配置、部署步骤和样片实验均为提案，尚未实施；未改变需求或冻结指标。

关联 M1-F04/F05/F06、M3-F01/F03/F04/F05/F06，FR08–FR15/FR18/FR19、NFR01–NFR08、AC04–AC10/AC14–AC17。依据 [AGENTS](../../../AGENTS.md)、[一键流程](../../../specs/ONE_CLICK_FLOW.md)、[M1规格](../../../specs/M1-capability-validation.spec.md)、[M3规格](../../../specs/M3-media-pipeline.spec.md)。产品流程保持：三项上传 → 一键完整未审核草稿 → 播放下载 → 教师主动确认。

## 3. 对四项实现疑点的核实

1. **逐页新进程：确实存在。** [Pipeline.native](../../../mooc_m3/pipeline.py)每次构建LocalModelAdapter；[generate](../../../mooc_m1/adapters.py)先health，再启动独立 `mooc_m1.model_worker`。health还启动torch依赖探测进程，并执行git及全部配置权重摘要核查。第2代共43次新生成请求，因此有43次生成进程及相应运行时探测。health每次逻辑读取TTS约1.873GB、照片约1.184GB权重；21次＋22次至少约65.39GB摘要扫描，操作系统页缓存可能避免实际磁盘读取，不能把逻辑字节数当物理I/O时间。原生加载取证还有额外摘要扫描。
2. **batch_size=1：三类均显式固定。** [worker](../../../mooc_m1/model_worker.py)的TTS参数、SadTalker CLI和MuseTalk CLI均为1。SadTalker上游本地固定源码默认2，MuseTalk普通推理默认8、实时推理默认20；默认值不证明本机可用。SadTalker batch按同一音频的多帧分组，不是把多页音频混成一个请求。增批需测试帧顺序、补齐尾帧、显存及数值/质量，不能按batch大小直接声称线性加速。
3. **人物预处理重复：确实存在。** SadTalker每个请求建立新结果目录并重新执行照片 `CropAndExtract.generate`；同进程warm只保留实例，仍重新处理照片。单张照片的landmark/3DMM日志循环各不足1秒，但完整裁剪/初始化没有总计时，照片缓存主要带来一致性和复用机会，收益不能说成几十分钟。MuseTalk每页创建新ASCII工作目录、复制原视频，重新抽PNG、提坐标和VAE latent；目前传 `--saved_coord`，没有传 `--use_saved_coord`，且新目录没有跨页坐标缓存，所以只保存不复用。
4. **多次编码与检查：确实存在，但必须区分编码和封装。** SadTalker先写人脸小视频，full模式再解码粘回照片并用OpenCV写完整人物视频；上游 `save_video_with_watermark(..., watermark=False)` 使用 `-vcodec copy`，属于视频流复制/音频封装，不是再编码视频。之后本机逐页 `compose` 使用libx264/fast/CRF20，再由 `join` 对整课使用同设置重新编码。join特意解决AAC编码延迟和共同零点，不能直接改concat-copy就称等价。默认最终1080p不等于人物模型人脸512或1080p；当前固定是256人脸、full背景。

新人物在适配器完成时检查视频＋音频，复制进缓存时再检查视频；页面合成前后多次检查驱动音频，join重新检查每页视频。缓存命中时亦核对摘要、视频和音频。`MediaTools.inspect`每次先做SHA和ffprobe，视频完整解码一次，音频完整解码再运行静音/音量检测。可设计同一不可变摘要的检查收据、合并视频/音轨/静音检查的一次受控扫描；每个新文件、传输文件、最终文件和重启后真实性仍必须验证。检查策略或文件摘要变化就重新完整检查，不能仅凭mtime、大小或远端“成功”省略必要校验。

SQLite WAL持久化单工作进程保持可靠性，场景检查点会重写包含资源采样的整份JSON（原任务快照约2.2MB）。尚无锁等待/事务计时证明它是主瓶颈，当前不建议迁库或增加多个共享写库的工作进程。

## 5. 最小部署结构与改动位置

```text
本机 Vue / FastAPI / SQLite / 受控存储
  PPT解析及原页渲染、讲稿版本、GPT-SoVITS、真实时间轴
      ↓ RemotePhotoAdapter：照片摘要＋当前页音频＋配置＋幂等键
云端 HTTPS入口 → 持久化片段队列 → 单GPU常驻SadTalker
      ↓ 本地结果文件＋摘要＋时长＋模型取证＋计时/显存
本机下载到临时文件 → 完整校验 → 原子发布人物缓存
      ↓ 原有逐页合成 / 整片校验 / 四类导出 / 播放下载 / 主动确认
```

本机为唯一课程与审核权威。云端只持有片段请求索引及生成需要的受控素材副本，不持有PPT、参考音色原录音、完整讲稿或主任务数据库。不暴露本机8765给公网；由本机发起HTTPS上传、查询和下载，无需云端回调穿透家庭网络。

最小改造仅给 [Pipeline.native](../../../mooc_m3/pipeline.py) 的photo角色加可选adapter工厂；新增RemotePhotoAdapter及独立云端包，返回现有 `media_ready/output/native_model_record/native_loads` 结构中的本机已下载路径，继续走copied_native、publish_cache、compose与join。视频、TTS及普通首页保持现流程。当前local health依赖Windows路径和本地git，不可原封不动用来声明云端就绪；远端health必须区分服务存活、权重核对、模型加载及资源可用。当前capabilities的fee=0只适用于local，远端须返回计费来源/未知费用，不冒用免费能力声明。

第一版保持现有唯一工作进程，RemotePhotoAdapter异步提交远端后在本机同步轮询等待，改动最小，且能直接测云卡带来的收益。**此版本不会自动重叠下一页TTS与当前页云端人物。** 第二版才在同一个课程状态机里增加有界待处理页队列（例如2页）：TTS n+1、远端人物 n、本机compose n-1有限重叠，SQLite发布仍由唯一所有者完成；不能简单开第二个现有Service抢同库。此调度收益须另外测CPU/RAM竞争。

| HEAD/PUT `/v1/assets/{sha256}` | 内容寻址、所有者隔离、大小/类型/摘要核对；照片仅上传一次，支持分块/续传，完成前不入推理队列 |

| GET `/v1/portrait-jobs/{id}` | queued/loading/preprocessing/inferencing/encoding/validating/ready/failed/canceled；真实帧进度、输出与错误 |

### 常驻、缓存与批量

启动时固定版本核查一次，加载CropAndExtract/Audio2Coeff/AnimateFromCoeff。health检查收据绑定只读权重卷、内容摘要及worker构建，发现变化即失效；请求仍检查输入和有效参数。请求后释放驱动tensor、帧列表和临时引用，模型常驻；观察长页后RSS和reserved是否持续增长，不能把 `empty_cache` 当可靠的泄漏修复。

照片预处理键至少包含照片字节摘要、SadTalker提交、主/辅助权重摘要、预处理实现版本、full/256和裁剪参数；保存系数、裁剪图、crop_info及各自摘要，不保存上一次音频驱动系数来冒充新输入。原生推理中仍使用本次音频。人物成果键额外包含当前音频摘要、驱动参数、精度、batch/帧排序策略和worker实现版本。现有model_key包含repo/python等部署路径，迁往云端会改变键；首版保留旧本机缓存，新增远端缓存命名空间，不强制别名旧键、不清库。经等价验证后才能讨论按模型语义跨部署复用。

先batch1，再2/4/8递增，首版一个GPU请求在运行，其余排队。批量是单页多帧并行；跨页可以批量提交任务描述以减少HTTP往返，但保持各页独立当前音频、结果和恢复点。batch占用是模型＋激活＋上下文，并非简单“1.7GB乘batch”。建议峰值reserved不超过可用显存约75–80%的工程预算，留驱动/波动余量；这是测试保护条件，不是已冻结产品阈值。

### 断线、重启和回滚

本机在首次POST前，将幂等键、输入摘要、逻辑片段操作ID和预期模型构建持久化到现有job JSON；得到request_id后保存。幂等键不随网络重连或本机execution更新而变化。POST响应丢失时用原键查询/幂等重提交，不能新建随机请求重新付费。

断线期间云端继续执行，恢复后查询原请求；ready则仅续传并完整验证文件，failed才按有限策略创建关联的新尝试并保留旧错误。云端GPU进程重启可重载模型、复用已验证照片缓存和已完成片段；当前未发布片段可能重算，首版不宣称可从中间某帧继续。云端请求索引和结果若存临时盘丢失，不能保证恢复，因此必须绑定持久卷。轮询失败与模型失败分开，重连不消耗正式生成重试次数；实际模型失败仍遵守本机有限代次，不新增无限云端重试。

本机接收结果后，核对逻辑操作ID、照片/音频/模型/配置摘要、当前任务状态，再由当前execution事务发布。旧execution、被取消任务、过期输入的晚到结果保留为历史，不覆盖现任务、不标整课完成。原三代限制、有效片段复用和全部片段完成门槛不变。

新任务选择local/remote photo后固定该执行配置；云端不可用明确等待/失败，不自动上传或降级，不在不知云任务状态时自动本机重算。回滚时停止新远端提交、记录/尽力取消运行请求，后续任务切回local；已验证下载结果和全部旧成果/失败均保留。回滚本机代码不等于已停止远端租用与费用，须单独检查远端任务和实例。

## 7. 传输与按课时费用的计算方法

已保存的原课程：照片54,408字节，24页WAV合计46,425,376字节，人物MP4合计70,741,617字节。第9页音频5,249,324字节、人物7,983,716字节。只传照片一次和当前音频，返回人物；无需上传PPT或下载云端整课。

理论传输时间 `8×照片/上行带宽＋Σ8×音频/上行带宽＋Σ8×人物/下行带宽`，带宽为bit/s；再加握手、24页往返、排队、重连和校验。不改变音频格式制造提速。上下行各10Mbps时，整课净字节传输下限约93.8秒，第9页约10.6秒；各2Mbps时整课约7.82分钟。它们是算术下限，不是中国本机到某云地区实测。云端full人物尺寸/码率或编码器改变时，输出字节数亦变，必须重新计量。

按需实例：

```text
每课总费 = GPU实例小时价 × 实际计费存活小时
         + 独立CPU/RAM费用（若实例价未含）
         + 持久存储月费 / 当月实际课时数
         + 网络、税费及其它服务费

计费存活时间 = 启动/镜像拉取/模型加载 + 实际推理/编码
             + 等待本机TTS与上传下载 + 重试 + 闲置尾部
```

云卡买的是运行时间，不能把“12分钟课时”直接当“12分钟GPU租用”。若推理失败后付费重做一页，费用计入该课；多课时共用一次模型加载可摊销，但不能假定每月一定有很多课时。设备队列等待与请求耗时、计费耗时分别记录。

每次必须记录：输入摘要；代码/权重/runtime/worker；随机种子、batch与精度；model_loaded/预处理/成果缓存命中；从本机提交到可播放结果的墙钟；连接/上传/队列/加载/照片处理/音频特征和系数/Face Renderer/CUDA到CPU/照片粘回/编码/摘要和解码/下载/本机单页合成各区间；失败阶段、实际计费时间及租用价。

质量与完成检查：真实MP4、当前音频摘要与帧数/时长、视频及音轨完整解码、异常静音、25fps、相同原照片full尺寸、人物身份/头部与眨眼动态、嘴形与30秒不同音频响应、中文口型、面部伪影、长页漂移、首尾及页面连接。渲染帧差异仅证明输出变化，不能代替人工口型评分。把样片嵌入相同1080p布局盲看；不自动填写教师确认或冻结质量阈值。

额外故障对照只用样片：POST响应丢失、上传/下载断开、本机进程重启、云GPU进程重启、取消后晚到结果、损坏结果、错误音频摘要。要求重复POST返回同一逻辑请求且不重复GPU执行；已完成片段重启仅下载/校验，未发布片段可有限重做；所有失败保留。验证远端继续执行并不保证网络故障时立即停止费用。

## 9. 12分钟课程能多快，以及实施顺序

本机同模型/batch1的已有长页显示，仅渲染12分钟×25fps约需94–97分钟，还要语音、照片粘回、编码和校验。全24页模型构造只约2.2分钟；即使理想化去掉全部照片“请求总时间减native生成再扣构造”的开销，以及全部TTS非推理开销，也仅能从135.49估计减约14.34分钟至约121.15分钟，且这些开销不可能全部消失。CPU合成重叠还有有限空间。**本机先按约120–135分钟规划同类零缓存媒体任务**，这是估计而非SLA；当前没有保持模型/batch1且达到一小时以内的证据。batch或实现变化另行测量，不能据此宣称硬件绝对下限。30秒旧A/B样片波动也说明热状态不是自动更快。

云端第一版仍串行，采用全24页历史请求预算：

`T估计 = 本机语音16.37分钟＋其他6.15分钟＋人物112.96分钟/S＋云启动/网络/队列差额`

S是**完整人物请求**在云端相对本机的实测加速，必须含预处理、推理、人物编码和检查。若S仅测Face Renderer，不能套用该公式；应只缩放对应的94.82分钟循环，并保留其余部分。

| 完整人物请求加速假设S（未测） | 串行整课媒体估计，不含云启动和传输增量 |
| --- | ---: |
| 2倍 | 79.01分钟 |
| 4倍 | 50.77分钟 |
| 6倍 | 41.35分钟 |
| 8倍 | 36.65分钟 |

因此，云端若小样片证明完整人物快4–6倍，12分钟课程可先预算约41–51分钟再加启动/网络，这是条件测算，不是RTX4090已证实速度。第二版有界流水线可让TTS和远端人物部分重叠，近似按两阶段最大值加填充/排空和最终编码估算；真实CPU资源竞争、逐页时长不均及恢复成本未测，不承诺20分钟。保持本机TTS时，未优化的16.37分钟语音阶段本身也限制目标。上述均只计讲稿已就绪后的媒体阶段；首次三项上传到整片还需PPT/ASR/讲稿耗时。

建议顺序：

1. 保存这份诊断作为分析基线。下一轮先做样片专用细粒度计时和远程契约/本地模拟恢复，保持现有默认运行；不开始整课。
2. 在明确设备、预算与素材云端范围后，准备单GPU独立镜像和持久卷。先RTX4090 24GB或实际可用的24GB候选，做R0：runtime兼容、30秒＋82秒batch1输出与质量。
3. 若R0质量可接受，逐项加入模型常驻、照片预处理缓存，再增batch；每项独立计时和回滚，69.34秒补验OOM边界。不一次改变GPU、精度、模型和编码。
4. 用样片验证幂等、断线续传、两端重启、取消和损坏结果；落实本机下载后原子发布，才能采纳最小远程photo adapter。
5. 样片测出卡时总费用后再比较L4/A10/3090等候选，并决定有界TTS/人物/合成重叠；必要时优化校验重复和编码链。
6. MuseTalk Avatar复用作为视频路径独立专项；新照片模型只在同SadTalker云端方案仍达不到质量/速度目标时进入候选验证。整课验证留到小样片方案已证明可用、用户授权下一轮执行之后。

当前可以推荐部署结构与验证顺序；无法确认具体GPU的项目加速倍数、实际每课时费用、云端质量是否等价、峰值RAM和地区链路。它们应由上述小规模对照补证，不能由官方演示、显存容量、历史局部重做或工程回归替代。
